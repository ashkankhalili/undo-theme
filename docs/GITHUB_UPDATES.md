# GitHub release and WordPress update workflow

The customer update channel is the public `ashkankhalili/undo-theme` GitHub repository. The theme folder and text domain stay `undo-theme`; the separate addon folder and text domain are `undo-elements`. Both use the repository as their `Update URI`. WordPress checks the latest published GitHub Release and offers newer versions in **Dashboard → Updates**. An administrator chooses when to install them. Automatic background installation is not enabled.

## One-time bootstrap

The 0.2.2 theme did not contain an updater, so it could not discover 0.2.3 by itself. The owner installed the verified 0.2.3 release ZIP. The owner then confirmed that WordPress offered 0.2.4 in **Dashboard → Updates** without another upload. The old update-details link tried to embed GitHub and failed. The owner confirmed that the WordPress-hosted popup displayed 0.2.6 release notes and installed the update; the owner later confirmed the 0.2.9 static-header fix on staging. The owner installed 0.3.0 and reported the page width mismatch; 0.3.1 and 0.3.2 corrected the page cases. The 0.3.3 release added page template controls; 0.4.0 added sidebar controls; 0.5.0 added the settings workspace, colors, and typography. The separate addon begins at 0.1.0 alongside theme 0.11.0 and needs one manual plugin ZIP install before its own updater can discover later versions.

## For each later version

1. Develop and review the change. Bump the theme version in `undo-theme/style.css`, `undo-theme/functions.php`, and `undo-theme/readme.txt`; update its translation catalog header in `tools/build-translations.mjs`. If the addon changes, separately bump `undo-elements/undo-elements.php`, `undo-elements/readme.txt`, and the header in `tools/build-addon-translations.mjs`. The addon asset version need not equal the theme version. Refresh accurate product descriptions and changelogs.
2. Regenerate POT/PO/MO files with `node tools/build-translations.mjs` and `node tools/build-addon-translations.mjs`. Add useful version-specific notes to the root, theme and addon changelogs and document any migration. The GitHub Release body is copied from the root changelog and appears in WordPress update details.
3. Run the relevant staging tests and merge the reviewed change to `main`. GitHub Actions runs PHP syntax and updater checks, translation and JavaScript checks, then builds and checks an installable `undo-theme-X.Y.Z.zip` and `undo-elements-A.B.C.zip`, each with exactly one product folder at the ZIP root.
4. After checks pass, the release job creates `vX.Y.Z` at the tested commit, attaches both exact ZIPs and their `.sha256` files, and verifies each published asset digest. Every theme release includes the current addon ZIP even when its version stays the same. A changed package at an existing version fails; bump the product version instead of replacing a release asset.
5. Check the GitHub Actions run, tag commit, Release page, both ZIP roots, asset names, and SHA-256 values. Test updates on staging from older installed versions before any customer announcement.
6. On staging, open **Dashboard → Updates → Check Again**, confirm the new version and release details, install the theme update, and verify the installed version, settings, menus, Elementor pages, translations, and PHP log. Install the addon ZIP manually for its first release; later test addon dashboard updates from a higher addon asset version. Record screenshots and results in `docs/staging-reports/`.

Both updaters use only exact versioned GitHub Release ZIPs; they never install GitHub's generated source archives. Each requires a SHA-256 digest from GitHub's asset metadata or the matching `.sha256` asset, then checks the downloaded bytes before WordPress replaces the product. Failed or malformed release metadata offers no update. The GitHub repository and release packages are public; customer-only downloads and license-based eligibility require a separate future decision and infrastructure. Never place a GitHub token in either ZIP.
